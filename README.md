# Code Visualisation Experiments

A set of experiments exploring code visualisation for Rust projects.

## Dimensions

- Titles
- Lines
- Layouts
- Labels
- Colors
- Orientations
- Shapes
- Keys
- Responsabilities

## How it works

The server scans a Rust project into nested folders, files, and semantic code
elements. It builds deterministic structure, source, and call-hierarchy layouts.
The structure map uses header-only code cards, while the source map flows each file in byte order
through 80-character columns capped at 100 visual lines. Minimal declaration
titles such as `struct Cell` and `fn run` use twice the source font size.

## Build and run

```bash
rustup component add rust-analyzer rust-src
rust-analyzer scip /path/to/rust/project --output /path/to/rust/project/index.scip
cd frontend
npm install
npm run build
cd ..
cargo run -- /path/to/rust/project
```

Open the tokenized URL printed by the server. The server requires `index.scip`
at the project root. If it is missing, startup prints the exact command needed
to generate it and exits. If Rust source files are newer than the index, startup
warns but continues.

## Navigation

- Wheel or pinch to zoom around the pointer.
- In `Structure` with `Source` enabled, zooming out cross-fades from full source
  into folder/file/chunk labels and then into folder/file labels.
- Drag to pan.
- Double-click a district or source card to focus it.
- In compact structure mode, hover a leaf or `impl` card for 250ms to open its
  full, scrollable source preview.
- Use `Structure` and `Calls` to switch the primary layout. `Source` independently
  toggles between compact cards with hover previews and inline source, and its
  state persists when switching layouts.
- The call hierarchy starts with functions that have no resolved project caller.
  In `Public only`, a public function nested beneath another public entry point is
  omitted from the root level. Mutually recursive public groups use the
  alphabetically first full path as their stable root.
  Recursive and repeated calls become terminal references, so every callable's
  source is rendered once. With inline source enabled, repeated and recursive
  references still provide their source on hover.
- Tree-sitter identifies call expressions, while SCIP supplies their semantic
  symbols and project definitions. There is no name-based fallback. Ambiguous
  calls are marked `(?)` and list their candidates on hover.
- Trait/interface calls are shown as `(dispatch)` groups containing their
  project implementations. Use `Unresolved calls` to show or hide unmatched
  calls and semantically resolved dependency calls, which are labelled
  `(external)`; both are hidden by default.
- Project macros participate as callable nodes. Calls generated by macro
  expansion cannot be inferred without compiler expansion.
- Tests are hidden by default. Use `Tests` to include items inside
  `#[cfg(test)]` and functions marked with `#[test]` or attributes such as
  `#[tokio::test]`; the setting applies to both primary layouts.
- Use `Public only` to retain declarations with any `pub(*)` visibility,
  `#[macro_export]` macros, public-trait members, and the ancestor containers
  needed to show them. The filtered layouts load on first use and are cached.
- Trait implementations are included with a syntax-based approximation: their
  target type's final name must match a public type in the scanned project.
- In call mode, `Public only` starts from public callables but retains reachable
  private implementation functions.
- Press `+`, `-`, or `0` to zoom or reset.
- Hold Shift while dragging to select source text.
